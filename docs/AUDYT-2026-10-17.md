## 🔴 Bezpieczeństwo i stabilność

### S1. `secret_key` w repozytorium — *w toku (Codex)*
`searxng-settings.yml` zawiera prawdziwy klucz; README sam zabrania publikacji sekretów.
- Klucz z `.env`, w pliku placeholder. **Wymiana klucza na serwerze** —
  stary pozostaje w historii gita.
- **Sukces:** `grep -r secret_key` nie zwraca wartości hex; instancja startuje z kluczem z `.env`.

### S2. Wyszukiwanie blokuje cały serwer
`web_search` jest funkcją synchroniczną z blokującym `httpx.get/post`.
FastMCP (mcp 1.30, `func_metadata.py`) wywołuje funkcje synchroniczne
bezpośrednio w pętli zdarzeń — podczas jednego wyszukiwania (do 10 s SearXNG
+ 20 s Perplexity) stoją UI, inne wywołania MCP i `/api/search`.
- `async def web_search` + `httpx.AsyncClient`
  (albo `anyio.to_thread.run_sync` dla obecnej logiki).
- **Sukces:** test — dwa równoległe wyszukiwania z atrapą opóźnioną o 1 s
  kończą się w < 1,5 s łącznie.

### S3. `/mcp` bez uwierzytelnienia
Każdy, kto dosięgnie portu lub sieci `ai`, może wyszukiwać i zużywać limit Perplexity.
Przy wystawieniu poza localhost (Cloudflare) to publiczna usługa.
- Opcjonalny token `MCP_AUTH_TOKEN` (nagłówek `Authorization: Bearer`) dla `/mcp`;
  brak tokenu w konfiguracji = zachowanie jak dziś (tylko localhost/sieć).
- **Sukces:** test — przy ustawionym tokenie żądanie bez nagłówka → 401, z nagłówkiem → 200.

### S4. Surowe wyjątki w odpowiedzi MCP
`errors.append(f"searxng: {e}")` — treść wyjątków (adresy wewnętrzne, statusy)
trafia do klienta MCP. `/api/search` to filtruje, `/mcp` nie.
- Zwracać kody (`searxng_timeout`, `searxng_http_error`, `perplexity_no_key`,
  `perplexity_limit`…), szczegóły tylko do logu.
- **Sukces:** test — wyjątek z tekstem `http://searxng:8080` nie pojawia się w wyniku narzędzia.

### S5. Kontener jako root, obraz `:latest`
`mcp/Dockerfile` bez `USER`; `searxng/searxng:latest` bez przypiętej wersji.
- `USER` nieuprzywilejowany; przypięta wersja obrazu SearXNG i zakres `mcp` w `requirements.txt`.
- **Sukces:** `docker compose exec mcp-search id -u` ≠ 0; compose bez `:latest`.

## 🔗 Kontrakt z wirralAI (oba repozytoria muszą się zgadzać)

Sprawdzone: schemat narzędzia generowany przez FastMCP
(`query: string` wymagane, `max_results: integer`) **jest zgodny** z walidacją
`McpSearchClient::definition()` w wirralAI.

### K1. „Brak wyników” wygląda jak awaria
Gdy SearXNG zwraca pusto, a Perplexity nie ma klucza, serwer zwraca
`source: null`. wirralAI dopuszcza tylko `searxng` / `perplexity-fast`
→ użytkownik dostaje błąd `provider_response` zamiast „brak wyników”.
- Dodać jawny `status`: `ok` | `empty` | `error` (pole addytywne, `source` bez zmian).
- wirralAI: `empty` → komunikat „brak wyników”, nie błąd.
- **Sukces:** test kontraktowy po obu stronach na tym samym przykładowym JSON.

### K2. Różne limity długości zapytania
UI: 500 znaków, narzędzie MCP: brak limitu i brak odrzucenia pustego zapytania,
wirralAI: 1000.
- Walidacja w `web_search`: niepuste, ≤ 1000 znaków.
- **Sukces:** test — puste i 1001-znakowe zapytanie odrzucone bez wywołania SearXNG.

### K3. Wersja protokołu MCP
wirralAI akceptuje listę wersji protokołu; `mcp>=1.2,<2` może po aktualizacji
zwrócić nowszą i zerwać połączenie.
- Przypiąć wersję `mcp`; aktualizować świadomie razem z listą w wirralAI.
- **Sukces:** `requirements.txt` z konkretną wersją; wpis w CHANGELOG obu repo przy zmianie.

### K4. Wspólny przykład kontraktu
- Plik `docs/contract/web_search.example.json` (ok / empty / error) skopiowany
  do testów obu repozytoriów.
- **Sukces:** testy obu repo czytają te same przykłady.

## 🟡 Jakość

### Q1. Licznik Perplexity w pamięci procesu
Restart zeruje limit; brak blokady przy równoległych wywołaniach.
- `threading.Lock`; opcjonalnie zapis licznika do pliku w wolumenie.
- **Sukces:** test — 100 równoległych wywołań przy limicie 50 daje dokładnie 50.

### Q2. `.env.example` nie odpowiada README
Zawiera `APP_ENV` / `APP_DEBUG`, brak zmiennych z README
(`PPLX_API_KEY`, `PPLX_DAILY_LIMIT`, `SEARXNG_LANG`, `SEARCH_*`).
- **Sukces:** każda zmienna z tabeli README jest w `.env.example` (pusta).

### Q3. Czytelność
`server.py`: `import os, json, datetime, httpx` w jednej linii, długie warunki
w `web_app.py` i `api.js` (walidacja wyniku w jednym wyrażeniu).
- Wydzielić `is_valid_result()` / `isValidResult()` z nazwanymi krokami.
- **Sukces:** `ruff` / linter czysty; walidacja czytelna jednym spojrzeniem.
